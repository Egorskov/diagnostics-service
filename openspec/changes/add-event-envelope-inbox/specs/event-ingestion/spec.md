# Spec Delta

## Purpose

Приём входящих событий других сервисов из RabbitMQ: разбор общего конверта, превращение события в типизированное сообщение, однократная обработка по `event_id` и сохранность сообщений, которые не удалось разобрать или обработать (SPEC §4, §9).

## ADDED Requirements

### Requirement: Разбор конверта
Сервис SHALL принимать сообщения только в конверте `asyncapi.yaml → Envelope`: JSON-объект с обязательными `event_id` (UUID), `event_type`, `event_version` (целое ≥ 1), `occurred_at` (ISO 8601), `producer`, `payload` (объект) и необязательным `correlation_id` (UUID). Время из конверта MUST храниться и передаваться дальше в UTC.

#### Scenario: Валидный конверт
- **WHEN** приходит сообщение с корректным конвертом события MVP
- **THEN** сервис передаёт на обработку событие с метаданными конверта и разобранным payload

#### Scenario: occurred_at со смещением
- **WHEN** `occurred_at` равен `2026-10-30T12:00:00+01:00`
- **THEN** метаданные события содержат момент `2026-10-30T11:00:00Z`

#### Scenario: Без correlation_id
- **WHEN** в конверте нет `correlation_id`
- **THEN** событие принимается, `correlation_id` в метаданных пустой

#### Scenario: Не хватает обязательного поля
- **WHEN** в конверте нет `event_id`, или `event_version` не целое, или тело не JSON
- **THEN** событие не обрабатывается и сохраняется как непринятое (см. «Непринятые сообщения не теряются»)

### Requirement: Поддерживаемые события
Сервис SHALL обрабатывать события MVP (SPEC §10) `path.assigned`, `task.started`, `task.completed`, `time.logged`, `activity.heartbeat`, `sandbox.run` версии `event_version = 1`. Payload MUST проверяться на обязательные поля, типы и допустимые значения перечислений из `asyncapi.yaml`.

#### Scenario: Payload по контракту
- **WHEN** приходит `sandbox.run` с `run_id`, `student_id`, `task_id` и `result = failed`
- **THEN** событие принимается с этими значениями; отсутствующие необязательные поля (`error_type`, `tests_passed`, `tests_total`) пустые

#### Scenario: path.assigned со списком заданий
- **WHEN** приходит `path.assigned` с полным снапшотом пути (SPEC §4, `PathSnapshot`)
- **THEN** событие содержит каждое задание с `task_id`, `stage_id`, `estimate_minutes`, `position`

#### Scenario: Значение вне перечисления
- **WHEN** `activity.heartbeat` приходит с `source = video`
- **THEN** событие сохраняется как непринятое

#### Scenario: Неизвестный тип события
- **WHEN** приходит валидный конверт с `event_type`, которого нет среди событий MVP
- **THEN** событие сохраняется как непринятое с причиной «неизвестный тип»

#### Scenario: Неподдерживаемая версия
- **WHEN** приходит `task.completed` с `event_version = 2`
- **THEN** событие сохраняется как непринятое с причиной «неподдерживаемая версия»

### Requirement: Однократная обработка по event_id
Сервис SHALL изменять своё состояние по событию не более одного раза для каждого `event_id` (SPEC §5 `inbox_event`, §9). Отметка об обработке MUST фиксироваться атомарно с изменениями, которые сделала обработка.

#### Scenario: Повторная доставка
- **WHEN** событие с тем же `event_id` доставлено второй раз после успешной обработки
- **THEN** обработка не выполняется повторно, сообщение подтверждается брокеру

#### Scenario: Обработка упала
- **WHEN** обработка события завершилась ошибкой
- **THEN** ни изменения, ни отметка об обработке не сохраняются, и событие можно обработать повторно

#### Scenario: Одновременная доставка дубликатов
- **WHEN** два экземпляра консьюмера одновременно получают события с одинаковым `event_id`
- **THEN** изменения состояния применяются ровно один раз

### Requirement: Ретраи при ошибке обработки
Если обработка события завершилась ошибкой, сервис SHALL повторить её до 3 раз с экспоненциально растущей задержкой (SPEC §9). Повтор MUST доставляться только в очередь Диагностики, не другим подписчикам исходного exchange.

#### Scenario: Временная ошибка
- **WHEN** первая попытка обработки падает, а вторая проходит
- **THEN** событие обработано один раз, в failure transport не попадает

#### Scenario: Ретраи исчерпаны
- **WHEN** все 4 попытки (первая и 3 повтора) завершились ошибкой
- **THEN** событие сохраняется как непринятое (см. «Непринятые сообщения не теряются»)

### Requirement: Непринятые сообщения не теряются
Сообщение, которое не удалось разобрать (конверт, тип, версия, payload) или обработать после всех ретраев, SHALL сохраняться в failure transport (SPEC §9 «DLQ») вместе с исходным телом и причиной. Неразобранные сообщения MUST попадать туда без ретраев. О каждом таком сообщении MUST писаться запись уровня error с `event_id` и `correlation_id`, когда они известны.

#### Scenario: Неразобранное сообщение
- **WHEN** приходит сообщение с невалидным конвертом
- **THEN** оно сразу, без ретраев, оказывается в failure transport с исходным телом и причиной, в логе — запись уровня error

#### Scenario: Просмотр и повтор
- **WHEN** оператор смотрит failure transport
- **THEN** он видит непринятые сообщения и может отправить их на повторную обработку

### Requirement: Отдельный поток для heartbeat
События `activity.heartbeat` SHALL приниматься из отдельной очереди, чтобы их поток не задерживал остальные события (SPEC §9 «Нагрузка»). Сервис MUST подписываться только на routing keys событий MVP.

#### Scenario: Всплеск heartbeat
- **WHEN** в очереди heartbeat накопились тысячи сообщений
- **THEN** события `task.completed` из очереди Курсов принимаются без ожидания разбора этой очереди

#### Scenario: Событие бэклога
- **WHEN** Курсы публикуют `quiz.answered` в `courses.events`
- **THEN** сообщение не попадает в очереди Диагностики
