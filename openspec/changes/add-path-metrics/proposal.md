# Proposal

## Why

Шаг 5 MVP (CLAUDE.md «Текущий скоуп», п. 5; SPEC §6.2, §10): после шагов 3–4 у сервиса есть путь ученика, оценки заданий, статусы, списанное время и активное время, но ни одной метрики прогресса. EV/PV/AC, SPI/CPI и прогноз — основа `GET /students/{id}/summary` и сортировки по риску в `GET /mentor/students` (шаг 7), без них Read-API показывать нечего.

## What Changes

- Расчёт метрик пути ученика по SPEC §6.2 в Domain, чистым PHP без базы и фреймворка:
  - `EV` — сумма оценок закрытых заданий пути;
  - `PV` — `min(Σ оценок, недельная цель × недель с начала)`, недели дробные;
  - `AC` — сумма списанного времени по заданиям пути;
  - `SPI = EV / PV`, `CPI = EV / AC`, не считаются при нулевом знаменателе;
  - плановая дата завершения, прогноз завершения и отставание в днях.
- Табличные юнит-тесты на каждую формулу, включая пример ответа из SPEC §8 (`ev 2700, pv 3600, ac 3300 → spi 0.75, cpi 0.82`).
- Уточнения там, где §6.2 молчит (недели меньше четырёх, путь закрыт, нулевая цель, календарная дата): решения в `design.md`, требования в спеке.

Вне скоупа:
- Сбор входных данных из базы, порты и use case — шаг 7 (Read-API), там же округление SPI/CPI в JSON.
- Регулярность, баланс и расхождение из §6.2 — не входят в п. 5 MVP, понадобятся для `summary` на шаге 7.
- Сигналы, в т.ч. `student.at_risk` (бэклог SPEC §10), и пороги из §7.1 — метрикам шага 5 пороги не нужны.
- Таймзона ученика и дедлайны заданий (PV по дедлайнам) — бэклог SPEC §10.

`SPEC.md` и `asyncapi.yaml` не меняются.

## Capabilities

### New Capabilities
- `path-metrics`: метрики прогресса ученика по пути — EV/PV/AC, SPI/CPI, плановая дата, прогноз и отставание (SPEC §6.2).

### Modified Capabilities

Нет.

## Impact

- Новый код только в `src/Domain/Metrics/` и `tests/Unit/Domain/Metrics/`.
- База, миграции, очереди, хендлеры и контракты не меняются. Новых зависимостей нет.
