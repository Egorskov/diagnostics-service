# Design

## Context

Мотивация — proposal.md, требования — `specs/`.

Что есть после шагов 3–4:
- `student_path` хранит `started_at` и `weekly_goal_minutes`, `path_task` — состав пути и оценки;
- `TaskProgress::complete()` всегда ставит `completed_at` вместе со статусом `completed`, поэтому `completed_at` однозначно говорит, закрыто ли задание и когда (ADR 0003: при повторе берётся раннее время);
- `time_log` хранит списания с `task_id` или без него.

Шаг 5 по CLAUDE.md — «Domain + тесты». Метрики никто не вызывает до шага 7, поэтому сбор данных из базы откладывается туда, где станет понятно, какие запросы нужны API.

## Goals / Non-Goals

**Goals:**
- Все формулы §6.2 из п. 5 MVP в одном месте, без Doctrine, Symfony и часов.
- Каждое правило и граница покрыты табличным тестом.

**Non-Goals:**
- Порты, запросы, кеширование и хранение посчитанных метрик.

## Decisions

### 1. Слои и классы

| Часть | Слой | Где |
|---|---|---|
| `PlannedTask` — оценка, `completedAt`, списанные минуты одного задания пути | Domain | `src/Domain/Metrics/` |
| `PathPlan` — `startedAt`, `weeklyGoalMinutes`, список `PlannedTask` | Domain | `src/Domain/Metrics/` |
| `PathMetrics` — результат и фабрика `PathMetrics::calculate(PathPlan, now, zone)` | Domain | `src/Domain/Metrics/` |

Отдельный namespace `Metrics`, а не `Progress`: в `Progress` лежат сущности с маппингом, а здесь неизменяемые value objects, которые не сохраняются.

Метрики принимают свои value objects, а не сущности `StudentPath`/`TaskProgress`: на шаге 7 данные удобнее собрать одним запросом, а `/mentor/students` считает метрики сразу для многих учеников, и поднимать ради этого сущности незачем.

*Альтернатива:* stateless-сервис `PathMetricsCalculator`. Состояния у расчёта нет, а фабрика на результате даёт один класс вместо двух.

### 2. Списания приходят на задание, а не суммой
`PlannedTask` несёт минуты, списанные по этому заданию, а `AC` — их сумма. Тогда правило «только задания пути» выполняется само: задания вне пути и списания без задания в `PathPlan` просто не попадают. Запрос шага 7 — `GROUP BY task_id` по заданиям пути.

*Альтернатива:* передавать готовый `AC` числом. Проще, но правило отбора уходит целиком в SQL, и тесты шага 5 его не проверяют.

### 3. «Сейчас» и зона — аргументы
`calculate()` получает момент `now` и `\DateTimeZone`, а не `ClockInterface`: чистая функция тестируется без подмены часов, а вызывающий код шага 7 возьмёт `now` из `ClockInterface`, как требует CLAUDE.md. Зона приходит аргументом, потому что в бэклоге таймзона ученика (SPEC §10); пока вызывающий код передаёт Europe/Belgrade. Конфигурации зоны в проекте нет: Belgrade упомянут только в комментарии расписания.

### 4. Недели дробные, минуты целые
Пример §8 даёт `PV` = 3600 при цели 1500, то есть 2,4 недели: недели с начала считаются дробно, `(now − started_at)` в секундах / 604 800. `PV` — целые минуты, дробная часть отбрасывается, как у активного времени шага 4, чтобы план не обгонял факт на минуту.

`SPI`/`CPI` — `float` без округления; `null`, когда знаменатель 0. До сотых округлит API.

### 5. Даты — календарные дни, переход в днях с округлением вверх
Плановая дата и прогноз — `\DateTimeImmutable` на полночь даты в переданной зоне. Недели переводятся в дни (`× 7`) и округляются вверх: работа, которой осталось на 2,3 дня, закончится на третий день. Дата начала — дата `started_at` в той же зоне. Отставание — разность дат в днях, со знаком.

### 6. Темп при коротком пути (уточнение §6.2)
§6.2 делит EV за 4 недели на 4. Для пути младше 4 недель это занижает темп: через неделю после старта прогноз вышел бы в четыре раза дальше реального. Поэтому делитель — дробное число недель с начала, ограниченное снизу 1 и сверху 4. Нижняя граница нужна, чтобы одно задание в первый день не давало темп в десятки раз выше реального. Для пути старше 4 недель поведение совпадает со спекой буквально.

Окно — `[now − 28 суток, now]` по `completed_at`, обе границы включены, как и граница таймаута сессии на шаге 4. Задания пути, закрытые до окна, входят в `EV`, но не в темп.

*Альтернатива:* буквально `/ 4`. Тогда первые недели прогноз заметно пессимистичнее, а сигнал `student.at_risk` в бэклоге построен на SPI, не на прогнозе — на сигналы это не влияет, только на то, что увидит ученик.

### 7. Крайние случаи
- Все задания закрыты: прогноз — дата последнего `completed_at`, иначе пройденный путь «заканчивался бы» каждый день заново, а отставание росло бы.
- Темп 0 при незакрытых заданиях: прогноз `null`. Деления на ноль нет, «никогда» показывать нечем.
- `weekly_goal_minutes` ≤ 0: в `asyncapi.yaml` у поля нет `minimum`. `PV` = 0 по формуле, плановая дата `null`.
- Пустой путь: `EV` = `PV` = `AC` = 0, прогноз `null` (закрывать нечего), плановая дата — дата начала.

## Risks / Trade-offs

- [Уточнение темпа (решение 6) расходится с буквальным §6.2 для путей младше 4 недель] → для остальных совпадает; спеку дополнить по просьбе (Open Questions).
- [Расчёт не проверен на реальных данных до шага 7] → пример §8 проверяет связку формул; на шаге 7 проверим через API на эмулированном потоке.
- [`/mentor/students` считает метрики по всем ученикам ментора на каждый запрос] → расчёт в памяти линеен по заданиям; если станет тяжело, на шаге 7 можно хранить агрегаты.

## Migration Plan

Миграций нет: новый код ничего не хранит и ничем не вызывается до шага 7. Откат — revert коммитов.

## Open Questions

- SPEC §6.2 стоит дополнить делителем темпа для короткого пути (решение 6) и правилом для пройденного пути (решение 7). Менять спеку без просьбы нельзя, поэтому уточнения живут здесь; реализацию ответ не меняет, только формулировку §6.2.
