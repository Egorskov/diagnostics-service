# Spec Delta

## Purpose

Правила сигналов MVP о неактивности, застревании и отставании от недельной цели, их пороги и дедупликация по переходу состояния (SPEC §7.1–7.3). Диагностика сообщает факт, а доставку решают Уведомления.

## ADDED Requirements

### Requirement: Дедупликация по переходу состояния
Состояние сигнала SHALL храниться по ключу (тип, аудитория, ученик, предмет): предмет — задание для `task.stuck`, понедельник недели для `weekly_goal.behind`, пусто для `student.inactive`. Сигнал MUST публиковаться только при переходе условия из ложного в истинное (SPEC §7.3). Пока условие истинно, повторные проверки ничего не публикуют. Когда условие стало ложным, состояние сбрасывается без публикации, и следующий переход — новый сигнал.

#### Scenario: Повторная проверка
- **WHEN** условие истинно на двух проверках подряд
- **THEN** опубликован один сигнал

#### Scenario: Сброс и повтор
- **WHEN** условие стало ложным, а затем снова истинным
- **THEN** опубликовано два сигнала, второй — после нового перехода

#### Scenario: Аудитории независимы
- **WHEN** у ученика активен сигнал для аудитории `student`
- **THEN** сигнал для аудитории `mentor` публикуется по своему условию

### Requirement: Текущий путь ученика
Правила SHALL брать ментора и недельную цель из пути ученика с самым поздним `started_at`, при равенстве — с наибольшим `path_id`. Ученики без пути MUST NOT проверяться правилами `student.inactive` и `weekly_goal.behind`. `mentor_id` в сигнале — ментор этого пути (`SignalBase`).

#### Scenario: Два пути
- **WHEN** у ученика пути от 2026-09-01 и 2026-10-01 с разными менторами
- **THEN** сигнал несёт `mentor_id` пути от 2026-10-01

### Requirement: Последняя активность
Последняя активность ученика SHALL равняться самому позднему `last_seen_at` его сессий активности, с заданием или без (SPEC §3, §6.1). Если сессий нет, за последнюю активность MUST приниматься `started_at` текущего пути. Списание времени активностью не считается.

#### Scenario: Сессии есть
- **WHEN** последняя сессия ученика закончилась 2026-10-30T10:00:00Z
- **THEN** последняя активность — 2026-10-30T10:00:00Z

#### Scenario: Ученик ни разу не занимался
- **WHEN** у ученика нет сессий, текущий путь начат 2026-10-01T00:00:00Z
- **THEN** последняя активность — 2026-10-01T00:00:00Z

### Requirement: Неактивный ученик
Ежечасная проверка SHALL публиковать `diagnostics.student.inactive` с аудиторией `student`, когда с последней активности прошло не меньше `inactive_student_days` суток, и с аудиторией `mentor` — не меньше `inactive_mentor_days` (SPEC §7.2). Payload: `days_inactive` — целые сутки с последней активности, `last_activity_at` — последняя активность. Появилась активность — состояние сбрасывается на следующей проверке.

#### Scenario: Три дня
- **WHEN** последняя активность 3 суток назад при порогах 3 и 7
- **THEN** опубликован сигнал с аудиторией `student` и `days_inactive` = 3, сигнала ментору нет

#### Scenario: Почти три дня
- **WHEN** последняя активность 2 суток и 23 часа назад
- **THEN** сигнала нет

#### Scenario: Семь дней
- **WHEN** последняя активность 7 суток назад, сигнал ученику уже активен
- **THEN** опубликован сигнал с аудиторией `mentor`, ученику повторно не опубликован

#### Scenario: Ученик вернулся
- **WHEN** после сигнала пришла точка активности, а затем прошла проверка
- **THEN** состояния обеих аудиторий сброшены, сигнал не опубликован

### Requirement: Застревание — сигнал ученику
На `sandbox.run` и `activity.heartbeat` с заданием, у которого есть прогресс, SHALL проверяться условие: задание не закрыто и активное время > `stuck_time_ratio` × оценки или неудачных запусков ≥ `stuck_failed_runs` (SPEC §7.2). Истинное условие публикует `diagnostics.task.stuck` с аудиторией `student`, ложное сбрасывает состояние. `reason` — `time_exceeded`, если превышено время, иначе `failed_runs`.

#### Scenario: Время превышено
- **WHEN** оценка 60, порог 1,5, heartbeat довёл активное время до 91
- **THEN** опубликован сигнал с `reason` = `time_exceeded`, `active_minutes` = 91, `estimate_minutes` = 60

#### Scenario: Ровно полторы оценки
- **WHEN** оценка 60, активное время 90
- **THEN** сигнала нет

#### Scenario: Десятый неудачный запуск
- **WHEN** `sandbox.run` с `result` = `failed` довёл `failed_runs` до 10
- **THEN** опубликован сигнал с `reason` = `failed_runs`, `failed_runs` = 10

#### Scenario: Оба условия
- **WHEN** превышено время и `failed_runs` ≥ 10
- **THEN** опубликован один сигнал с `reason` = `time_exceeded`

#### Scenario: Задания нет в пути
- **WHEN** у прогресса нет оценки, потому что задания нет в составе пути
- **THEN** проверяется только условие по неудачным запускам, `estimate_minutes` в payload не передаётся

#### Scenario: Задание закрыто
- **WHEN** приходит `task.completed` по заданию с активным сигналом
- **THEN** состояния сигналов задания для обеих аудиторий сброшены, сигнал не опубликован

### Requirement: Застревание — эскалация ментору
Ежечасная проверка SHALL публиковать `diagnostics.task.stuck` с аудиторией `mentor`, если сигнал ученику по заданию активен, с его последней публикации прошло не меньше `stuck_escalation_hours` часов и задание не закрыто (SPEC §7.2). Payload — как у сигнала ученику, по текущим значениям прогресса. Если условие застревания к этому моменту ложно, эскалации нет, а состояние ученика сбрасывается.

#### Scenario: Прошли сутки
- **WHEN** сигнал ученику опубликован 24 часа назад, задание не закрыто
- **THEN** опубликован сигнал с аудиторией `mentor`

#### Scenario: Прошло меньше суток
- **WHEN** сигнал ученику опубликован 23 часа назад
- **THEN** эскалации нет

#### Scenario: Повторная проверка после эскалации
- **WHEN** эскалация уже опубликована, задание всё ещё не закрыто
- **THEN** повторно ментору не опубликовано

### Requirement: Отставание от недельной цели
Ежечасная проверка SHALL после момента `weekly_goal_check` текущей недели публиковать `diagnostics.weekly_goal.behind` с аудиторией `student`, если списано меньше `weekly_goal_min_ratio` × `weekly_goal_minutes` (SPEC §7.2). Неделя — с понедельника по воскресенье по `logged_for_date` в Europe/Belgrade. Payload: `goal_minutes`, `logged_minutes` — все списания ученика за неделю, `week_start` — понедельник. Ученики с целью ≤ 0 не проверяются.

#### Scenario: Отстаёт в четверг вечером
- **WHEN** четверг 18:00 Europe/Belgrade, цель 1500, за неделю списано 540
- **THEN** опубликован сигнал с `logged_minutes` = 540 и `week_start` — понедельник этой недели

#### Scenario: Половина цели
- **WHEN** к проверке списано 750 при цели 1500
- **THEN** сигнала нет

#### Scenario: До момента проверки
- **WHEN** четверг 17:00, списано 0
- **THEN** сигнала нет

#### Scenario: Следующая неделя
- **WHEN** сигнал был на прошлой неделе и в этот четверг ученик снова отстаёт
- **THEN** опубликован новый сигнал с новым `week_start`

#### Scenario: Списание без задания
- **WHEN** за неделю есть списание без `task_id`
- **THEN** оно входит в `logged_minutes`

### Requirement: Пороги правил
Пороги правил MUST читаться из таблицы порогов при каждой проверке (SPEC §7.1, ADR 0004). Начальные значения SHALL совпадать с §7.1: `inactive_student_days` = 3, `inactive_mentor_days` = 7, `weekly_goal_check` = `четверг 18:00 Europe/Belgrade`, `weekly_goal_min_ratio` = 0.5, `stuck_time_ratio` = 1.5, `stuck_failed_runs` = 10, `stuck_escalation_hours` = 24. Отсутствующий или неразборчивый порог MUST приводить к ошибке проверки без изменения состояний.

#### Scenario: Начальные значения после миграций
- **WHEN** применены все миграции на пустой базе
- **THEN** все семь порогов равны значениям §7.1

#### Scenario: Значение изменено
- **WHEN** `inactive_student_days` = 5, последняя активность 4 суток назад
- **THEN** сигнала нет

#### Scenario: Порога нет на событии
- **WHEN** нет строки `stuck_failed_runs` и приходит `sandbox.run`
- **THEN** обработка события завершается ошибкой, прогресс и состояния сигналов не изменились
