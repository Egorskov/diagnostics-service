# Design

## Context

Мотивация описана в proposal.md, требования — в `specs/`.

Что уже есть после шагов 2–7:
- Транспорты `courses`, `time` и `heartbeat` (AMQP) привязаны к exchange `courses.events`, `time.events` и `activity.events`. Их сериализатор `EnvelopeSerializer::encode()` отправляет тело из `RawBodyStamp` байт-в-байт и ставит `Content-Type: application/json`. Сейчас этим пользуются только ретраи.
- `AmqpSignalPublisher` уже отправляет сообщение прямо в sender транспорта, мимо шины, с `AmqpStamp(routing key)`.
- Пороги читаются через порт `Thresholds`: `stuckTimeRatio()`, `inactiveStudentDays()`, `weeklyGoalMinRatio()`, `weeklyGoalCheck()`.
- ADR 0003: события из разных очередей могут прийти не по порядку. Без контекста падает только `sandbox.run` (`UnknownTaskProgress`), его спасают ретраи.
- В `Makefile` уже есть цель `emulate` с вызовом `bin/console app:emulate-events $(ARGS)`. Каталога `src/UI/Console/` пока нет.
- В функциональных тестах транспорты in-memory и без сериализации. `EventFlowTestCase::deliver()` кладёт в транспорт уже разобранный конверт.

## Goals / Non-Goals

**Goals:**
- Генератор детерминирован: одинаковые входные данные (seed, опции, `now`, пороги) дают одинаковый поток. Поэтому его можно тестировать без брокера.
- Публикация идёт ровно тем путём, которым придут события настоящих продюсеров: exchange, routing key, тело и заголовки.

**Non-Goals:**
- Правдоподобная статистика поведения: распределения, выходные, таймзона ученика.
- Запуск консьюмеров и Scheduler из команды.

## Decisions

### 1. Слои и классы

| Часть | Слой | Где |
|---|---|---|
| `EmulateEventsCommand` — опции, валидация, вывод | UI | `src/UI/Console/` |
| `Profile` (enum), `Scenario` (входные данные), `ScenarioGenerator` → `list<EmulatedEvent>` | UI | `src/UI/Console/Emulator/` |
| `EmulatedEvent` — транспорт, `event_type`, конверт-массив, `json()` | UI | `src/UI/Console/Emulator/` |
| `MessengerEventPublisher` — отправка в sender транспорта | UI | `src/UI/Console/Emulator/` |

Эмулятор изображает внешних продюсеров и не входит в доменную логику Диагностики, поэтому весь живёт в `UI/Console` (CLAUDE.md, «Архитектура»). В Domain и Application ничего не добавляется. Зависимость UI → `Infrastructure\Messenger\RawBodyStamp` допустима: это тот же формат «сырого тела», которым пользуются ретраи. Отдельный порт ради одного потребителя был бы лишней абстракцией.

### 2. Публикация — sender транспорта с `RawBodyStamp` и `AmqpStamp`

`MessengerEventPublisher` берёт sender `messenger.transport.{courses|time|heartbeat}` и отправляет `Envelope(EmulatedEvent, [RawBodyStamp(json), AmqpStamp(event_type)])`. Как и у `AmqpSignalPublisher`, это делается мимо шины: шина нашла бы для `EmulatedEvent` маршрут или хендлер, а нам нужна только отправка. `EnvelopeSerializer::encode()` берёт тело из стампа, а exchange задан конфигом транспорта.

Почему так:
- **Конфиг exchange в одном месте.** Его не нужно дублировать в эмуляторе, как пришлось бы при прямом AMQP-клиенте или вызовах management API.
- **Маршрут продюсера.** Exchange → binding → очередь проходится так же, как у продюсера.
- **Тесты без брокера.** В тестовом окружении sender — in-memory. Тест достаёт тело из `RawBodyStamp` и подаёт его в `deliver()`. Так проверяется и то, что сериализатор разбирает каждое событие.

Отвергнуто:
- Прямой `php-amqplib`/`ext-amqp` — дублирует конфиг.
- Отправка через шину с роутингом `EmulatedEvent` на транспорты — меняет `messenger.yaml` ради инструмента.

### 3. Сценарий: путь, сессии, задания

Всё время считается в Europe/Belgrade (`app.timezone`) и хранится в UTC.

**Путь.**
- 6 заданий в 2 этапах, виды чередуются `theory` / `sandbox`.
- Оценки — из набора 120…480 мин, выбираются генератором.
- Недельная цель — 600 мин.
- `started_at` — 09:00 дня, наступившего `--days` дней назад.

**Учебный день.**
- Одна сессия с 18:00. В день старта пути, если он сегодня, сессия начинается не раньше `started_at`.
- Длина сессии зависит от профиля (решение 4). Сессия обрезается текущим моментом, и событий после `now` нет.
- Внутри сессии ученик работает над текущим заданием (первое незакрытое по `position`):
  - первое касание задания — `task.started`;
  - затем heartbeat каждые 60 с с `task_id` и `source`: `theory`, если задание теоретическое, иначе `sandbox`;
  - у заданий `sandbox` каждые 20 мин — `sandbox.run` с результатом `failed`.
- Задание закрывается, когда накопленные активные минуты достигают оценки × коэффициент. У `steady` коэффициент от 0,8 до 1,2. Перед закрытием `sandbox`-задания — `sandbox.run` `passed`, затем `task.completed`. Остаток сессии идёт на следующее задание.
- В конце сессии — `time.logged` на активные минуты по каждому заданию сессии, `logged_for_date` = дата сессии. Категория: `theory` → `theory`, `sandbox` → `practice`. По пятницам дополнительно 30 мин `interview` без задания, чтобы в балансе были все три категории.

**Сортировка.** События сортируются по `occurred_at`, при равенстве сохраняется порядок генерации. Так `task.started` всегда идёт раньше heartbeat того же момента.

**Нагрузка.** 14 дней `steady` дают около 1,5 тыс. heartbeat. Для RabbitMQ и одного воркера это немного, батчинг не нужен.

### 4. Профили — от порогов, а не от констант

Генератор получает `Thresholds` и подстраивает поток так, чтобы условие сигнала выполнялось при текущих порогах, а не при дефолтах SPEC.

| Профиль | Дни | Сессия | Особенность |
|---|---|---|---|
| `steady` | каждый день | 120 мин | задание закрывается при активном времени оценка × 0,8…1,2, но не больше 0,9 × `stuck_time_ratio` |
| `behind` | каждый день | ⌊(`weekly_goal_min_ratio` × 600 − 1) / 7⌋, не больше 30 мин | за неделю списано < `weekly_goal_min_ratio` × 600; без `interview` |
| `stuck` | каждый день | 120 мин, последняя — сколько нужно | в последней сессии текущее задание не закрывается, его активное время доводится до ⌊`stuck_time_ratio` × оценка⌋ + 16 мин |
| `inactive` | каждый день, кроме последних `inactive_student_days` + 1 | 120 мин | последняя точка активности раньше `now − inactive_student_days` |

**Без выходных.** Занятия идут каждый день. Иначе при короткой истории и пропущенном дне `steady` мог бы оказаться без единой сессии, а `inactive` — без учебного дня до паузы.

**Длина пути.** Заданий в пути не меньше 6, и их хватает на всю историю: ⌈(`--days` + 1) × 120 / минимальное время закрытия⌉ + 1. Если бы ученик закрыл весь путь, он перестал бы проявлять активность и попал бы под `student.inactive`.

**Неудачные запуски.** У всех заданий, кроме застрявшего задания `stuck`, неудачных `sandbox.run` меньше `stuck_failed_runs`. Иначе `task.stuck` сработал бы по второму условию §7.2.

**`steady` и недельная цель.** Генератор следит, чтобы неделя `steady` не попала под `weekly_goal.behind`. `WeeklyGoalCheck` проверяет каждый час, начиная с четверга 18:00 и до конца недели. Поэтому важно, сколько списано к этому моменту:
- При полной неделе к четвергу 18:00 списано 360 из 600, то есть 60% — выше порога 50%.
- Если путь начался на этой неделе (малый `--days`) и момент проверки уже прошёл, может не хватить. Тогда последний `time.logged` дополняется списанием `practice` без задания до ⌈`weekly_goal_min_ratio` × цель⌉ + 30 мин. Такое списание не влияет на AC (SPEC §6.2).

**`stuck` и `--days`.** Последняя сессия `stuck` идёт столько минут, сколько нужно для условия, но не меньше 120. Если она не помещается до `now`, она начинается раньше 18:00, но не раньше конца предыдущей сессии. Если не помещается и так (огромный `stuck_time_ratio` при `--days` = 1), команда завершается с ошибкой и просит увеличить `--days`.

**`inactive` и `--days`.** Профилю нужен хотя бы один учебный день до паузы. Поэтому при `--days` ≤ `inactive_student_days` + 1 команда завершается с `Command::INVALID` и называет минимальное значение.

**`behind`.** Сигнал публикует недельная проверка (Scheduler, четверг 18:00). Если запустить эмулятор в понедельник, сигнал придёт только в четверг вечером, при работающем `make consume`. Это видно в выводе команды: она печатает подсказку, какой проверки ждать.

### 5. Детерминизм и id

- Источник случайности — `Random\Randomizer(new Mt19937($seed))`.
- Без `--seed` seed берётся из `random_int` и печатается, чтобы запуск можно было повторить.
- Из того же генератора берутся:
  - `event_id` и `run_id` — UUID v4 из 16 случайных байт через `Uuid::fromBinary` с выставленными версией и вариантом;
  - id ученика, ментора, пути, заданий и этапов, если они не заданы опциями.
- `now` берётся из `ClockInterface`, поэтому в тестах время подменяется.

Одинаковый seed — одинаковые `event_id`. Повторная публикация целиком отсекается inbox. Это нарочно: так видна идемпотентность (SPEC §9). Чтобы получить нового ученика, запускают команду без `--seed` или с другим seed.

### 6. Порядок доставки

Внутри каждого exchange события уходят по времени. Между очередями порядок не гарантирован (ADR 0003). Heartbeat и `time.logged` самодостаточны. `sandbox.run` до обработки `task.started` падает с `UnknownTaskProgress` и проходит на ретрае. `make consume` читает `courses` раньше `heartbeat`, поэтому на практике ретраев почти нет. Эмулятор ничего специально не делает: он показывает систему такой, какая она с настоящими продюсерами.

### 7. Вывод команды

- Без `--dry-run`:
  - таблица `event_type → количество`;
  - id ученика, пути, ментора и seed;
  - два заглушечных токена в формате ADR 0006 (`sub`, `role`, без `exp`) и готовые строки `curl` для `localhost:8080`.
- С `--dry-run` — только NDJSON конвертов в stdout, по одному на строку, без таблицы. Так вывод можно передать в `jq` или в файл.
- Ошибки опций: `Command::INVALID` и сообщение в stderr, до генерации.

## Risks / Trade-offs

- [Генератор знает формулы сигналов] → Он не вызывает правила сигналов, а только строит поток с запасом над порогом. Функциональные тесты проверяют сигнал через настоящие хендлеры и проверки.
- [Токены в выводе] → Это заглушки без подписи, их принимает только MVP-authenticator (ADR 0006). Секрета в них нет.
- [`behind` зависит от дня недели запуска] → Это описано в выводе. В тесте время подменяется после четверга 18:00.
- [Тестовые данные в dev-базе остаются] → Эмулятор ничего не чистит: это обычные данные ученика. Другой ученик — другой seed.
