# Proposal

## Why

Шаг 8 MVP (CLAUDE.md «Текущий скоуп», п. 8; SPEC §10: «эмулятор входящих событий (console-команда)»). Сервис Курсов, фронт и учёт времени пока не публикуют события. Поэтому показать Диагностику целиком сейчас можно только ручными скриптами, которые собирают конверты по одному. Так было при ручных проверках шагов 3–7. Эмулятор генерирует правдоподобную историю одного ученика и публикует её в те же exchange, куда будут писать настоящие продюсеры. Дальше её обрабатывают обычные консьюмеры, а результат виден в Read-API и в `diagnostics.events`.

## What Changes

- Консольная команда `app:emulate-events`, запуск — `make emulate` (цель в Makefile уже есть):
  - генерирует историю одного ученика за последние `--days` дней (по умолчанию 14): `path.assigned`, затем по дням `task.started`, `activity.heartbeat` раз в 60 с (SPEC §4), `sandbox.run`, `time.logged`, `task.completed`;
  - конверты и payload строго по `docs/asyncapi.yaml`, `occurred_at` — в прошлом, события идут по возрастанию времени;
  - публикует в `courses.events`, `time.events` и `activity.events`, routing key = `event_type`, то есть тем же путём, что настоящие продюсеры.
- Профили поведения — аргумент `profile` (`app:emulate-events stuck`). Каждый, кроме `steady`, доводит ученика до условия одного из сигналов MVP (SPEC §7.2) с порогами из таблицы `threshold`:
  - `steady` — занимается регулярно, идёт около плана;
  - `behind` — за текущую неделю списано меньше `weekly_goal_min_ratio` недельной цели;
  - `stuck` — активное время на текущем задании больше `stuck_time_ratio` × оценка, задание не закрыто;
  - `inactive` — последняя активность раньше, чем `inactive_student_days` дней назад.
- Опции: `--student` и `--mentor` (UUID, по умолчанию генерируются), `--seed` для воспроизводимого потока, `--dry-run` — вывести события в stdout как NDJSON и ничего не публиковать.
- После публикации команда печатает id ученика, пути и ментора, число событий по типам и заглушечные токены ученика и ментора для Read-API (ADR 0006). С ними можно сразу проверить `curl`-ом.

`SPEC.md` и `asyncapi.yaml` не меняются. Новых зависимостей нет: нужны `symfony/console`, `symfony/messenger` и `symfony/uid`, они уже стоят.

Вне скоупа:
- События бэклога: `user.registered`, `path.updated`, `quiz.answered`, `hint.used`, `material.rated`, `assessment.completed`.
- Несколько учеников за запуск и нагрузочная генерация. При необходимости команду запускают несколько раз.
- Эмуляция нарушенного порядка, дублей и битых сообщений. Это уже покрыто тестами шагов 2–3.
- Эмулятор не запускает консьюмеры и Scheduler сам: обработку делает `make consume`.

## Capabilities

### New Capabilities
- `event-emulator`: генерация и публикация потока входящих событий одного ученика по профилю поведения (SPEC §4, §10).

### Modified Capabilities

Нет. Эмулятор только публикует события, обработка не меняется.

## Impact

- Новый код в `src/UI/Console/`: команда, генератор сценария и публикатор в транспорты Messenger.
- Публикация идёт через существующие транспорты `courses`, `time`, `heartbeat` и `EnvelopeSerializer` (тело — `RawBodyStamp`). Конфиг Messenger не меняется.
- Эмулятор читает пороги через порт `Thresholds`, поэтому ему нужна база с применёнными миграциями.
- Таблиц, миграций и ADR не добавляется.
