# Design

## Context

Мотивация — proposal.md, требования — `specs/`.

Что есть после шага 3:
- порт `ActivityTracker::record(ActivityPoint)`, его вызывают хендлеры `task.started`, `task.completed`, `sandbox.run`, `activity.heartbeat`; реализация — заглушка;
- хендлер работает в транзакции шины, `flush` делает `doctrine_transaction`, дубликаты отсекает inbox;
- `TaskProgressRepository::findForUpdate` блокирует строку. Проверено в `doctrine/orm`: `persist` с заданным ID кладёт сущность в identity map, поэтому прогресс, только что созданный хендлером `task.started`, находится этим же методом до `flush`;
- heartbeat — самый частый поток (SPEC §9).

## Goals / Non-Goals

**Goals:**
- Хендлеры шага 3 не меняются: заменяется только реализация порта.
- Формулы в Domain, покрыты табличными тестами.

**Non-Goals:**
- Батчинг heartbeat и кеширование порогов.

## Decisions

### 1. Слои и классы

| Часть | Слой | Где |
|---|---|---|
| `ActivitySession` | Domain | `src/Domain/Progress/` |
| `TaskProgress::updateActiveMinutes()` | Domain | `src/Domain/Progress/` |
| `Threshold` | Domain | `src/Domain/Threshold/` |
| `SessionActivityTracker` (реализация порта) | Application | `src/Application/Activity/` |
| Порты `ActivitySessionRepository`, `Thresholds` | Application | `src/Application/Port/` |
| Doctrine-реализации, маппинг, миграции | Infrastructure | `src/Infrastructure/Persistence/Doctrine/` |

Трекеру нужны только порты, поэтому он в Application, а не в Infrastructure, где лежала заглушка. Единственная реализация порта привязывается автоматически, конфиг не меняется.

### 2. Правила сессии — в `ActivitySession`
- `covers(at, idleMinutes)`: `started_at − idle ≤ at ≤ last_seen_at + idle`.
- `touch(at)`: `started_at` = минимум, `last_seen_at` = максимум.
- `minutes()`: `floor((last_seen_at − started_at) / 60) + 1`.

**Уточнение SPEC §6.1.** Шаг 2 буквально говорит: если `last_seen_at ≥ t − idle_timeout`, то `last_seen_at = t`. Для опоздавшей точки это условие истинно всегда, и она сократила бы сессию, причём точка недельной давности прикрепилась бы к сегодняшней. Спека там же требует писать опоздания больше таймаута отдельной сессией, поэтому добавлена нижняя граница окна, а границы только расширяются. Для точек по порядку поведение совпадает со спекой буквально.

Неполная минута отбрасывается: при heartbeat раз в 60 с результат ровно совпадает с формулой §6.1 и не завышает активное время.

Если под окно попадают две сессии, продлевается та, у которой `last_seen_at` позже. Склейки нет: опоздавшая точка между двумя сессиями продлит только одну, и в сумме получится на минуту-другую меньше, чем у одной сплошной сессии. Для MVP с допущением «примерно по порядку» это приемлемо.

### 3. Пересчёт суммы вместо приращения
`active_minutes` каждый раз считается как сумма длительностей всех сессий задания, что буквально повторяет §6.1, п. 5.

*Альтернатива:* прибавлять разницу длительностей до и после точки — одна операция вместо чтения сессий, но минуты точек, пришедших до появления прогресса, потерялись бы навсегда. С пересчётом они учитываются при следующей точке.

Трекер читает сессии задания сущностями и считает сумму в PHP, включая новую, ещё не сохранённую сессию. `SUM` в SQL её бы не увидел без лишнего `flush` посреди хендлера. Сессий одного ученика по одному заданию обычно единицы и десятки.

### 4. Два запроса: с заданием и без
- С заданием: `forTask(student, task)` возвращает все сессии, они нужны для суммы.
- Без задания: сумма не нужна, а таких сессий у ученика со временем становится много, поэтому `withoutTaskNear(student, at, idle)` выбирает только попавшие в окно.

Индекс `(student_id, task_id, last_seen_at)` обслуживает оба запроса и пригодится проверке `student.inactive` на шаге 6. Индекс описан в маппинге, поэтому попадёт в diff.

### 5. Блокировка
Для точки с заданием трекер сначала вызывает `findForUpdate`, а потом читает сессии. Блокировка прогресса выстраивает параллельные точки одного задания в очередь: второй воркер увидит сессию первого, а не откроет дубликат.

У точек без прогресса или без задания блокировать нечего. В редком случае параллельной обработки возможны две близкие сессии: без задания они не входят в `active_minutes`, а для задания без прогресса пересчёт при следующей точке учтёт обе, завысив время не больше чем на длину перекрытия. Брать advisory-блокировку на каждый heartbeat ради этого не стоит.

### 6. Порог читается при каждой точке
Порт `Thresholds::idleTimeoutMinutes(): int` читает строку `threshold` через ORM. Типизированный метод вместо `get('idle_timeout_min')` держит ключи и разбор значения в одном месте. `value` хранится как текст, потому что в §7.1 есть и нечисловые значения (`четверг 18:00`, `7, 14, 30, 60, 100`).

Кеша нет: воркер живёт долго и не заметил бы изменение значения, а чтение по первичному ключу дешёвое. Отсутствие или мусор в значении — ошибка обработки (по ADR 0003 контекста не хватает), подставлять значение из кода нельзя: CLAUDE.md запрещает хардкод порогов.

### 7. Начальное значение — отдельная миграция с данными
Схема `threshold` генерируется через `make diff`, как обычно. Строка `idle_timeout_min` = 15 добавляется отдельной миграцией, созданной `doctrine:migrations:generate` и написанной руками, через `INSERT … ON CONFLICT DO NOTHING`. **Это единственное отступление от правила «миграции только через diff»:** diff сравнивает схемы и данные породить не может. Сгенерированные миграции по-прежнему не правятся.

*Альтернатива 1:* консольная команда установки порогов. Её легко забыть, и без неё каждая точка падала бы с ошибкой, а миграция применяется и в тестовой базе, и при развёртывании одинаково.
*Альтернатива 2:* значение по умолчанию в коде — запрещено CLAUDE.md.

### 8. Сквозная часть — в ADR 0004
Способ хранения порогов, типизированный порт и миграция с данными пригодятся шагу 6. Фиксируются в `docs/adr/0004-thresholds.md`.

## Risks / Trade-offs

- [Запрос сессий и `FOR UPDATE` на каждый heartbeat с заданием] → запросы идут по индексу и первичному ключу, транзакция короткая. Нагрузку проверим, когда появится реальный поток; при необходимости есть батчинг на стороне Курсов (SPEC §9).
- [Минуты точек до появления прогресса не попадают в `active_minutes` до следующей точки] → `path.assigned` обычно приходит раньше обучения, а `task.started` сам вызывает пересчёт; остаётся редкий случай без следующей точки.
- [`activity_session` растёт без ограничения] → для MVP допустимо, очистка в бэклоге.
- [Миграция с данными не отображается в `doctrine:migrations:diff`] → сценарий спеки и интеграционный тест проверяют значение на базе после миграций.

## Migration Plan

`make diff` → `make migrate`, затем миграция с данными. Данных для переноса нет: до этого change точки отбрасывались. Сообщения в очередях обрабатываются по новым правилам сразу после деплоя. Откат: `doctrine:migrations:migrate prev` дважды и возврат заглушки из истории git; `active_minutes` при этом не обнуляется.

## Open Questions

- SPEC §6.1 стоит дополнить нижней границей окна из решения 2. Изменить спеку без отдельной просьбы нельзя, поэтому уточнение живёт здесь; на реализацию ответ не влияет.
