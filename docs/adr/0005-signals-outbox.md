# 0005. Сигналы: состояние, конверт и outbox

Статус: принято
Дата: 2026-11-03
Change: `openspec/changes/add-signals` (детали реализации — его `design.md`, решения 2, 3, 6, 7)

## Контекст

SPEC §7.3 требует публиковать сигнал на переходе состояния и хранить его в `signal_state`, а SPEC §9 — транзакционный outbox: запись сигнала в той же транзакции, что `signal_state`, затем relay в RabbitMQ. Конверт исходящих событий — `asyncapi.yaml → Envelope`, exchange — `diagnostics.events`. SPEC не говорит:
- как устроен ключ `signal_state`, когда `subject_id` пуст;
- чем сделан outbox и что с доставкой при сбоях;
- откуда в конверте сигнала `event_id` и `correlation_id`.

Шаг 6 MVP реализует три сигнала, остальные девять из §7.2 ждут в бэклоге и должны встать на те же решения.

## Решение

1. **Переход состояния.** Состояние хранится по ключу (тип, аудитория, ученик, предмет). Сигнал публикуется только при переходе условия ложь → истина; пока условие истинно, ничего не публикуется; ложное условие сбрасывает состояние без публикации. `first_emitted_at` — первая публикация, `last_emitted_at` — последняя, от неё отсчитываются эскалации.
2. **Ключ `signal_state` — строка** `тип|аудитория|ученик|предмет`. Колонки остаются как в SPEC §5, `subject_id` — текст и может быть пустым. Составной ключ Doctrine с `NULL` невозможен, а индекс `NULLS NOT DISTINCT` не генерируется `doctrine:migrations:diff`. Предмет выбирается так, чтобы ключ различал то, что должно давать отдельный сигнал: задание, неделя.
3. **Outbox — Doctrine-транспорт Messenger** `outbox` в таблице `messenger_messages`. Он пишет через то же соединение, поэтому сигнал коммитится и откатывается вместе с `signal_state`. Relay — хендлер этого транспорта, он отправляет конверт в AMQP-транспорт `signals`. Ретраи и failure transport — как у входящих событий (ADR 0002, п. 4).
4. **Маршрутизация.** Exchange `diagnostics.events` типа `topic`, routing key = `event_type` (например, `diagnostics.task.stuck`), тело — JSON конверта, `content_type` = `application/json`.
5. **Конверт.** `event_id` — новый UUID v7 (`symfony/uid`), `event_version` = 1, `producer` = `diagnostics`, `occurred_at` — момент перехода в UTC. `correlation_id` продолжает цепочку входящего события: его `correlation_id`, а если нет — его `event_id`. У сигналов из Scheduler цепочки нет.
6. **Доставка at-least-once.** Сбой между публикацией и подтверждением outbox даёт повтор с тем же `event_id`; подписчик дедуплицирует по нему, как наш inbox (ADR 0002, п. 6).
7. **Пороги правил** — из `threshold`, по ADR 0004, и читаются при каждой проверке, а не при сборке расписания.

## Последствия

- Новый сигнал = правило в Domain + проверка в Application + схема payload из `asyncapi.yaml`; состояние, outbox и relay работают без изменений.
- Публикация не зависит от доступности RabbitMQ в момент перехода: сигнал ждёт в `messenger_messages`.
- Подписчики обязаны быть идемпотентными по `event_id`; это нужно согласовать с командой Уведомлений вместе с SPEC §11, вопросы 7–8.
- В `outbox` сообщение лежит в формате PHP-сериализатора Messenger: читать его из других сервисов нельзя, это внутренняя очередь.
- `signal_state` и обработанные записи failure transport растут без ограничения — очистка в бэклоге.
