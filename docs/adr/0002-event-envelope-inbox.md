# 0002. Конверт событий, inbox и топология входящих очередей

Статус: принято
Дата: 2026-10-30
Change: `openspec/changes/add-event-envelope-inbox` (детали реализации — его `design.md`)

## Контекст

Все события приходят в общем конверте `asyncapi.yaml → Envelope` (SPEC §4); обработка должна быть идемпотентной по `event_id` через `inbox_event` (SPEC §5, §9), с ретраями и DLQ (SPEC §9), а `activity.heartbeat` — в отдельной очереди (SPEC §9 «Нагрузка»). SPEC не говорит:
- что делать с сообщением, которое не удалось разобрать, — с неизвестным `event_type` или версией;
- как устроены очереди Диагностики относительно exchange других сервисов;
- где именно в обработке проверять `event_id`.

На этих решениях будут стоять все консьюмеры (шаг 3) и outbox (шаг 6), поэтому они фиксируются здесь, а не только в design.md change.

## Решение

1. **Конверт → метаданные + DTO.** Метаданные конверта (`event_id`, `event_type`, `event_version`, `occurred_at` в UTC, `producer`, `correlation_id`) — value object в Application. Каждое входящее событие — типизированный DTO, который несёт эти метаданные. Хендлеры не видят JSON и транспорт.
2. **Поддерживаемое = тип + версия.** Сервис принимает пару (`event_type`, `event_version`), которую явно знает. Новая версия контракта — новый DTO или явная поддержка, а не «попробуем разобрать как старую».
3. **Неразобранное не теряется.** Невалидный JSON или конверт, неизвестный тип, неподдерживаемая версия, невалидный payload — сообщение сразу, без ретраев, уходит в failure transport с исходным телом и причиной и пишется в лог уровня error. Тихий ack и reject без DLQ не используются: потеря события исказила бы метрики (EV/AC), а сохранённое можно повторить, когда поддержка появится.
4. **Ошибки обработки:** 3 ретрая с экспоненциальной задержкой, затем тот же failure transport. Failure transport — в PostgreSQL (`symfony/doctrine-messenger`), чтобы непринятые сообщения можно было смотреть и повторять по одному.
5. **Топология: своя очередь на каждый exchange-источник.** Диагностика объявляет очереди `diagnostics.<источник>` и привязывает их к exchange отправителей только по routing keys событий, которые умеет обрабатывать. Сейчас: `courses.events` → `diagnostics.courses`, `time.events` → `diagnostics.time`, `activity.events` → `diagnostics.heartbeat`. Новый источник — новая очередь и транспорт; новое событие от того же источника — новый binding key.
6. **Inbox — в транзакции шины, до хендлера.** Отметка `event_id` в `inbox_event` делается в той же транзакции БД, что и изменения хендлера (`INSERT … ON CONFLICT DO NOTHING`); дубликат подтверждается брокеру без вызова хендлера. Хендлеры про идемпотентность не знают.

## Последствия

- Добавить консьюмер нового события = DTO + запись в реестр типов + binding key + хендлер; inbox, ретраи и обработка ошибок работают без изменений.
- Изменение контракта другой командой видно сразу (error в логе и failure transport), а не через неделю по странным метрикам.
- `inbox_event` растёт без ограничения — очистка в бэклоге.
- Мы объявляем exchange других сервисов при старте (идемпотентно для типа `topic` из asyncapi); при расхождении типа консьюмер не стартует — это осознанно громкая ошибка.
- Имена очередей `diagnostics.*` видны другим командам; согласуются вместе с SPEC §11, вопрос 8.
- Если владельцем `time.logged` окажутся Курсы (SPEC §11, вопрос 1), очередь `diagnostics.time` удаляется, а `time.logged` становится binding key `diagnostics.courses`.
