# 0004. Пороги и их начальные значения

Статус: принято
Дата: 2026-11-02
Change: `openspec/changes/add-activity-sessions` (детали реализации — его `design.md`, п. 6 и 7)

## Контекст

SPEC §5 и §7.1 задают таблицу `threshold (key, value)` с дефолтами, а CLAUDE.md запрещает хардкодить пороги. Первым порог понадобился сессионизации (`idle_timeout_min`), дальше их будут читать правила сигналов на шаге 6. SPEC не говорит, как код читает значения и откуда в таблице берутся дефолты.

## Решение

1. **Значение хранится текстом.** В §7.1 есть и числа, и расписания (`четверг 18:00`), и списки (`7, 14, 30, 60, 100`).
2. **Типизированный порт.** Код просит конкретный порог (`Thresholds::idleTimeoutMinutes(): int`), а не строку по ключу. Ключи и разбор значений собраны в одной реализации.
3. **Чтение без кеша.** Воркер живёт долго и не должен пропускать изменение значения; чтение по первичному ключу дешёвое.
4. **Ошибка вместо значения из кода.** Отсутствие или мусор в значении — ошибка обработки: контекста не хватает (ADR 0003, п. 3), событие уходит в ретраи и failure transport.
5. **Начальные значения — миграцией с данными.** Схема генерируется через `doctrine:migrations:diff`, а строки добавляет отдельная миграция, написанная руками, через `INSERT … ON CONFLICT DO NOTHING`. Это единственное исключение из правила «миграции только через diff»: diff сравнивает схемы и данные породить не может.
6. **Порог добавляет шаг, которому он нужен.** Строка и метод порта появляются вместе с кодом, который их читает.

## Последствия

- Новый порог = строка в миграции с данными + метод порта + разбор значения.
- База после миграций одинакова в разработке, тестах и при развёртывании; отдельной команды установки нет, забыть её нельзя.
- Настройка порогов ментором (бэклог SPEC §8) сможет менять строки таблицы без изменения кода чтения.
