# 0006. Аутентификация Read-API: заглушка JWT

Статус: принято (временное решение MVP)
Дата: 2026-11-04
Change: `openspec/changes/add-read-api` (детали реализации — его `design.md`, решения 2, 3, 10)

## Контекст

Пользователями и аутентификацией владеет сервис Auth (SPEC §2). SPEC §8 требует от Read-API принимать JWT от Auth и проверять подпись публичным ключом. Ученик должен видеть только себя, ментор — своих учеников. SPEC не говорит:
- в каких claims Auth передаёт пользователя и роль;
- где взять публичный ключ.

Справочника ролей у Диагностики пока нет: `user.registered` в бэклоге. CLAUDE.md для шага 7 разрешает заглушечный authenticator.

## Решение

1. **Токен.** Каждый запрос к `/api/v1` несёт `Authorization: Bearer <JWT>` в компактной форме `header.payload.signature`. Из payload читаются:
   - `sub` — идентификатор пользователя, тот же UUID, что `student_id` / `mentor_id` в событиях;
   - `role` — `student` или `mentor`;
   - `exp` — необязательный, Unix-время; если он задан и прошёл, токен отклоняется.
2. **Подпись на MVP не проверяется.** Заголовок, алгоритм и третья часть токена игнорируются. Любой, кто может отправить запрос, может представиться кем угодно, поэтому API нельзя выставлять за пределы доверенной сети, пока заглушка не заменена.
3. **Роль берётся из токена**, а не из базы. Пользователь не загружается: authenticator сразу строит его из `sub` и `role`.
4. **Ответы.** Если токена нет или он невалиден — 401 `{"error":"unauthorized"}`. Если пользователь аутентифицирован, но прав нет — 403 `{"error":"forbidden"}`. Права проверяют voter и роли Symfony Security, а не контроллеры.
5. **Инструмент** — `symfony/security-bundle`: stateless firewall на `^/api` и собственный authenticator.

## План замены

Когда Auth выдаст ключ и подтвердит claims (SPEC §11):
- authenticator начинает проверять подпись публичным ключом из конфигурации (алгоритм — из белого списка, а не из заголовка токена) и `exp`;
- при другом формате claims меняется только разбор payload;
- роли можно сверять с `user_role` после того, как появится консьюмер `user.registered`.

Контроллеры, voter и ответы 401/403 при этом не меняются.

## Последствия

- Все эндпоинты §8, включая бэклог, ставятся за тот же firewall и voter.
- Тесты и ручные проверки строят токены сами: base64url от JSON payload и произвольная подпись.
- До замены заглушки сервис безопасен только во внутренней сети. Это ограничение надо назвать при любой выкладке за пределы локального стенда.
